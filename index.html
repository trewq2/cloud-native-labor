02
Alapfogalmak

Felhőből Cloud Native

Virtuális gép vagy konténer?

A VM teljes vendég operációs rendszert futtat. A konténer a host kernelét használja, ezért kisebb és gyorsabban indul.

Image vagy container?

Az image sablon. A container az image futó példánya. Ugyanabból az image-ből több izolált példány indítható.

Miért registry?

A registry központi image-tároló. Az elkészített image más gépen vagy Kubernetes klaszteren is letölthető.

Miért Kubernetes?

Automatizálja a konténerek telepítését, skálázását, újraindítását és frissítését, és kívánt állapotot tart fenn.

GitHub Codespaces – fejlesztés a felhőben

Mit tanulsz? Megérted, hogyan lehet egy teljes Linux fejlesztői környezetet nem a saját gépeden, hanem egy felhőben futó környezetben használni.

1. Repository létrehozása

  1. Jelentkezz be a GitHubba.
  2. A jobb felső sarokban kattints a + jelre, majd válaszd a New repository lehetőséget.
  3. A repository neve legyen: cloud-native-labor.
  4. Állítsd Public értékre.
  5. Ne adj hozzá külön README-t, .gitignore-t vagy licencet; a starter csomag ezeket a szükséges fájlokat tartalmazza. Kattints a Create repository gombra.
Akkor jó: megnyílik az új repository és a fejlécben a cloud-native-labor név látszik.

2. A starter fájlok feltöltése – a repository GYÖKERÉBE

  1. Csomagold ki a letöltött cloudlab_starter.zip fájlt.
  2. Nyisd meg a kibontott mappát, és a benne lévő fájlokat és mappákat töltsd fel – ne magát a külső cloudlab_starter mappát.
  3. GitHubon kattints: Add file → Upload files.
  4. Töltsd fel az app.py, Dockerfile, compose.yaml, k8s.yaml, requirements.txt, check-compose.sh és status-site elemeket.
  5. Ellenőrizd külön, hogy a .github és .devcontainer mappa is felkerült. Windowsban a ponttal kezdődő mappák általában láthatók, de ezt mindig ellenőrizd a GitHub fájllistájában.
  6. Commit message: CloudLab starter projekt, majd Commit changes.
Akkor jó: a repository gyökerében közvetlenül látszik az app.py, Dockerfile, compose.yaml és k8s.yaml. Nem kell előbb cd starter parancsot kiadnod.
Ha a ponttal kezdődő mappák hiányoznak: GitHubon válaszd az Add file → Create new file lehetőséget. A fájlnév mezőbe írhatsz teljes útvonalat, például .devcontainer/devcontainer.json vagy .github/workflows/container-ci.yml. Így a GitHub létrehozza a mappákat is. A fájlok tartalmát a letöltött starter csomagból másold be.

3. Codespace indítása

  1. A repository főoldalán kattints a zöld Code gombra.
  2. Nyisd meg a Codespaces fület.
  3. Kattints a Create codespace on main gombra.
  4. Várd meg, amíg a böngészőben megjelenik a VS Code-szerű felület és alul a terminál.
Ha nincs Codespaces gomb: használd a helyi VS Code + Docker Desktop környezetet. A parancsok ugyanazok, csak a saját gépeden futnak.

4. Ellenőrizd, hogy jó helyen vagy

A listában keresd az app.py, Dockerfile, compose.yaml, k8s.yaml fájlokat. Ha a Dockerfile csak egy starter almappában látszik, állj meg: rossz könyvtárstruktúrát töltöttél fel.

test -f Dockerfile && echo "OK: repository gyökér" || echo "HIBA: nincs itt Dockerfile"
Elvárt: OK: repository gyökér.

5. Környezet verzióinak ellenőrzése

uname -a python --version git --version docker --version kubectl version --client
Akkor jó: egyik parancs sem ad „command not found” hibát.

6. Az alkalmazás indítása Pythonból

pip install -r requirements.txt python app.py

A terminálban ilyesmit kell látnod: Running on http://127.0.0.1:8080 vagy 0.0.0.0:8080.

  1. Codespaces-ben nyisd meg a PORTS fület.
  2. Keresd a 8080 portot.
  3. Kattints a földgömb / Open in Browser ikonra.
  4. A megnyíló oldalon írd az URL végére: /health.
Elvárt válasz: {"status":"ok"}.
Miért nincs még számláló? A sima python app.py futásnál nem indítottunk Redis szolgáltatást. A főoldalon ezért a Redis „Nincs konfigurálva ebben a futási módban” állapota helyes. A látogatásszámláló a 3. modul Docker Compose részében aktiválódik.
Ha a 8080-as port nem látszik: a PORTS panelen válaszd az Add Port lehetőséget és add meg: 8080. Ha a Python fut, de nincs oldal, ellenőrizd, hogy nem állítottad-e le a programot.

2. modul • 45 perc

Docker alapok – image, container, port és log

Mit tanulsz? Az image egy sablon, a container ennek futó példánya. Ebben a modulban egy kész Nginx image-ből indítasz és kezelsz konténereket.

1. Nginx image letöltése

docker pull nginx:alpine docker image ls
Akkor jó: a listában megjelenik az nginx repository és az alpine tag.

2. Első container indítása

docker run -d --name web1 -p 8081:80 nginx:alpine docker ps

A -p 8081:80 jelentése: a fejlesztői környezet 8081 portját a container 80 portjára kapcsoljuk.

curl http://127.0.0.1:8081
Akkor jó: HTML tartalmat kapsz vissza, benne az Nginx üdvözlőoldal szövegével.

3. Logok megtekintése

docker logs web1

A logban a korábbi HTTP kérésnek is meg kell jelennie.

4. Container életciklus

docker stop web1 docker ps docker ps -a docker rm web1

Figyeld meg a különbséget: docker ps csak a futó, a docker ps -a a leállított konténereket is mutatja.

5. Két container egyszerre

docker run -d --name web-a -p 8081:80 nginx:alpine docker run -d --name web-b -p 8082:80 nginx:alpine docker ps curl http://127.0.0.1:8081 curl http://127.0.0.1:8082
Elvárt állapot: két futó Nginx container, egyik a 8081, másik a 8082 host porton.
Ha „port is already allocated” hiba jelenik meg: egy másik container már használja a portot. Nézd meg: docker ps, majd állítsd le a zavaró konténert vagy válassz másik host portot.
Ha „container name is already in use” hibát kapsz: töröld a régi példányt: docker rm -f web-a.
Bizonyíték 03: docker image ls az Nginx image-dzsel.
Bizonyíték 04: docker ps, amelyen egyszerre látszik a web-a és web-b container, valamint a két különböző port.
3. modul • 45 perc

Saját Docker image, Compose, Redis, volume és Docker Hub

Mit tanulsz? A Dockerfile segítségével reprodukálható image-et építesz. Docker Compose-zal két szolgáltatást – a webalkalmazást és Redist – kapcsolsz össze.
Ha új órán folytatod: nyisd meg újra a repository Codespace-ét. Futtasd: docker ps -a. Ha a korábbi konténerek nem futnak, ez nem hiba – ebben a modulban újra felépítjük őket.

1. Dockerfile értelmezése

Nyisd meg a Dockerfile fájlt. Keresd meg benne:

  • FROM – melyik alap image-ből indulunk;
  • WORKDIR – hol dolgozunk a containeren belül;
  • COPY – mely fájlokat másoljuk be;
  • RUN – melyik parancs fut image build közben;
  • CMD – mi indul el a container indulásakor.

2. Saját image buildelése

docker build -t cloudlab:1.0 . docker image ls
Akkor jó: megjelenik a cloudlab image 1.0 taggel.

3. Saját container tesztelése – Redis nélkül

docker run -d --name cloudlab -p 8080:8080 cloudlab:1.0 docker ps curl http://127.0.0.1:8080/health curl http://127.0.0.1:8080/api/info
Elvárt: a health válasz OK, az info válaszban az app értéke cloudlab. Az önálló containerben redis:false / redis_configured:false nem hiba, mert még nem indítottunk Redis szolgáltatást.

4. Compose – web + Redis, Codespaces-kompatibilis módon

Állítsd le az előző önálló containert, mert a Compose projekt is a 8080-as portot fogja használni:

docker rm -f cloudlab 2>/dev/null || true docker compose down --remove-orphans docker compose up -d --build --force-recreate docker compose ps

A listában két szolgáltatást kell látnod: web és redis. A Redis állapota legyen healthy.

Miért különleges a compose.yaml? GitHub Codespaces alatt Docker-in-Docker környezetben előfordulhat, hogy a hagyományos Docker bridge hálózaton a web → redis:6379 kapcsolat timeoutol. Ezért a starterben a web szolgáltatás a Redis hálózati névterét használja: network_mode: "service:redis". Így a két külön konténer ugyanazon hálózati névtérből éri el egymást, és a Flask a 127.0.0.1:6379 címen kapcsolódik a Redishez.

4/A. Redis önellenőrzés

docker compose exec -T redis redis-cli ping
Elvárt: PONG.

4/B. Web container → Redis kapcsolat

docker compose exec -T web python -c "import redis; r=redis.Redis(host='127.0.0.1',port=6379,socket_connect_timeout=2,socket_timeout=2); print(r.ping())"
Elvárt: True. Ha ez megvan, a Python alkalmazás valóban eléri a Redist.

4/C. API és látogatásszámláló ellenőrzése

curl http://127.0.0.1:8080/api/info curl -s http://127.0.0.1:8080/ >/dev/null curl -s http://127.0.0.1:8080/ >/dev/null docker compose exec -T redis redis-cli GET cloudlab_visits
Akkor jó: az API-ban "redis":true, a Redis parancs pedig egy növekvő számot ad vissza. A PORTS → 8080 → Open in Browser nézetben az F5 minden alkalommal növeli a látogatásszámlálót.
Gyors automatikus ellenőrzés: a starterben található check-compose.sh. Futtasd: bash check-compose.sh. Egyben ellenőrzi a Redis PING-et, a Python → Redis kapcsolatot, az API-t és a számlálót.
Ha a számláló nem nő: először docker compose ps, majd docker compose exec -T redis redis-cli ping, végül a fenti Python Redis teszt. Ne módosíts hálózati subnetet találomra. A starter működő Codespaces-beállítása a network_mode: "service:redis" és REDIS_HOST=127.0.0.1.

5. Tartós adat – volume teszt

  1. Nyisd meg többször a főoldalt. A látogatásszámláló növekedjen.
  2. Jegyezd fel az aktuális számot.
  3. Állítsd le a teljes Compose projektet, de ne töröld a volume-ot.
docker compose down docker volume ls docker compose up -d curl http://127.0.0.1:8080
Elvárt: a számláló nem nulláról indul újra, mert a Redis adata a volume-ban megmaradt.
Fontos: a docker compose down -v törölné a volume-ot is. Ebben a feladatban ezt még ne használd.

6. Docker Hub repository

  1. Jelentkezz be a Docker Hub weboldalára.
  2. Hozz létre egy új, Public repositoryt cloudlab néven.
  3. Jegyezd fel pontosan a Docker Hub felhasználónevedet.
  4. A terminálban jelentkezz be. Ha kétlépcsős hitelesítést használsz, jelszó helyett Docker Hub access tokent használj.
docker login -u SAJAT_DOCKERHUB_NEV docker tag cloudlab:1.0 SAJAT_DOCKERHUB_NEV/cloudlab:1.0 docker push SAJAT_DOCKERHUB_NEV/cloudlab:1.0
Akkor jó: Docker Hub webfelületén a cloudlab repositoryban látszik az 1.0 tag.
Ha „denied: requested access to the resource is denied”: általában hibás a Docker Hub felhasználónév, nincs bejelentkezve a CLI, vagy nem a saját repositorydat tageled.
Bizonyíték 05: saját cloudlab:1.0 image a terminálban.
Bizonyíték 06: egy képen vagy egymást követő képeken: docker compose ps, Redis PONG, Python Redis teszt True, valamint működő/növekvő cloudlab_visits számláló.
Bizonyíték 07: Docker Hub weboldal, cloudlab:1.0 taggel. Titkos tokent ne mutass!
4. modul • 45 perc

Kubernetes alapok – Deployment, Pod és Service

Mit tanulsz? A Kubernetesben nem közvetlenül „konténert indítasz”, hanem egy kívánt állapotot írsz le. A Deployment gondoskodik a Podokról, a Service stabil hálózati elérést ad.
Fontos: a Kubernetes-modul szándékosan csak a CloudLab webalkalmazást telepíti, Redis nélkül. Itt a fő cél a Deployment, Service, skálázás, self-healing és rollout. Ezért Kubernetesben a /api/info redis:false értéke helyes.

1. Kubernetes labor megnyitása

  1. Nyisd meg a Killercoda weboldalt.
  2. Válassz egy Kubernetes playground / Kubernetes alapú környezetet.
  3. Várd meg, amíg a terminálban használható a kubectl.
kubectl cluster-info kubectl get nodes
Akkor jó: legalább egy Kubernetes node Ready állapotú.

2. A k8s.yaml átmásolása a laborba

A GitHub repositorydban nyisd meg a k8s.yaml fájlt, majd kattints a Raw gombra és másold ki a böngésző címsorából a nyers fájl URL-jét.

curl -L -o k8s.yaml IDE_MASOLD_A_RAW_URLT ls -l k8s.yaml cat k8s.yaml

3. Docker Hub név beállítása

A YAML-ban a DOCKERHUB_FELHASZNALO helyére a saját felhasználóneved kell.

sed -i 's/DOCKERHUB_FELHASZNALO/SAJAT_DOCKERHUB_NEV/g' k8s.yaml grep image k8s.yaml
Akkor jó: a grep már a te felhasznalonev/cloudlab:1.0 image-edet mutatja.

4. Deployment és Service létrehozása

kubectl apply -f k8s.yaml kubectl get deployments kubectl get pods -o wide kubectl get services
Elvárt: a Deployment READY értéke 2/2, és két cloudlab-... Pod Running állapotú.

5. A szolgáltatás tesztelése a klaszteren belül

Ez a módszer online laborban is megbízható, mert nem igényel külső böngészős porttovábbítást:

kubectl run curltest --rm -it --restart=Never \ --image=curlimages/curl -- \ http://cloudlab/health
Elvárt válasz: {"status":"ok"}.

6. Nézd meg, mit hoztál létre

kubectl describe deployment cloudlab kubectl get pods kubectl get svc cloudlab
Ha ImagePullBackOff: ellenőrizd, hogy a Docker Hub repository Public-e, a felhasználónév helyes-e, és valóban létezik-e az 1.0 tag.
Ha CrashLoopBackOff: nézd meg a hibát: kubectl logs POD_NEVE és kubectl describe pod POD_NEVE.
Bizonyíték 08: kubectl get pods -o wide két Running Poddal.
Bizonyíték 09: a klaszteren belüli /health teszt sikeres válasza.
5. modul • 45 perc

Kubernetes üzemeltetés – scaling, self-healing és rollout

Mit tanulsz? A Kubernetes folyamatosan igyekszik fenntartani az általad előírt állapotot. Ha 4 Podot kérsz, 4-et tart fenn; ha egy eltűnik, újat hoz létre.
Ha a Kubernetes online laborod már lejárt: indíts új Kubernetes playgroundot, majd ismételd meg a 4. modul 2–4. lépését: töltsd le a k8s.yaml fájlt, írd át benne a Docker Hub nevet és add ki a kubectl apply -f k8s.yaml parancsot. Csak akkor folytasd, ha ismét 2 Running Podod van.

1. Skálázás 2-ről 4 Podra

kubectl scale deployment cloudlab --replicas=4 kubectl get deployment cloudlab kubectl get pods
Akkor jó: a Deployment READY értéke 4/4.

2. Self-healing megfigyelése

  1. Add ki: kubectl get pods.
  2. Másold ki az egyik cloudlab Pod teljes nevét.
  3. A következő parancsban a POD_NEVE helyére ezt írd.
kubectl delete pod POD_NEVE kubectl get pods

Futtasd néhányszor a kubectl get pods parancsot. Egy új, más nevű Pod jelenik meg, mert a Deployment továbbra is 4 replikát vár el.

Ez a self-healing: te töröltél egy példányt, a Kubernetes automatikusan pótolta.

3. Rollout létrehozása konfigurációváltozással

Ahelyett, hogy ugyanazt az image-et állítanánk be újra, módosítunk egy környezeti változót. Ez valódi új rolloutot indít:

kubectl set env deployment/cloudlab APP_VERSION=k8s-1.1 kubectl rollout status deployment/cloudlab kubectl rollout history deployment/cloudlab
Akkor jó: a rollout sikeresen befejeződik és a history legalább két revisiont mutat.

4. Ellenőrizd az új verziót

kubectl run infotest --rm -it --restart=Never \ --image=curlimages/curl -- \ http://cloudlab/api/info
Elvárt: a JSON-ban a verzió k8s-1.1.

5. Opcionális rollback

kubectl rollout undo deployment/cloudlab kubectl rollout status deployment/cloudlab

Ez visszaállítja az előző Deployment revisiont. Ha ezt elvégzed, utána újra ellenőrizd az /api/info választ.

Ha egy Pod Pending: használd a kubectl describe pod POD_NEVE parancsot. Az Events rész megmutatja, miért nem indult el.
Bizonyíték 10: 4/4 replica.
Bizonyíték 11: törlés után újonnan létrejött Pod és ismét 4 Running példány.
Bizonyíték 12: rollout history vagy sikeres k8s-1.1 API-válasz.
6. modul • 45 perc

CI/CD – GitHub Actions és Cloudflare Pages

Mit tanulsz? A CI azt jelenti, hogy a forráskód változása után automatikusan ellenőrzések futnak. A projekt workflow-ja Docker image-et épít és HTTP health-checket hajt végre.

1. A workflow fájl megkeresése

A repositoryban nyisd meg: .github/workflows/container-ci.yml.

Keresd meg benne ezt a három fő lépést:

  • Docker image build;
  • container indítása;
  • curl --fail .../health health-check.

2. Készíts egy kis módosítást

Codespaces-ben nyisd meg az app.py fájlt és módosíts egy látható szöveget, például:

git status git add . git commit -m "CloudLab CI teszt" git push

Ezután GitHubon kattints az Actions fülre.

Akkor jó: a legújabb Container CI futás zöld pipával fejeződik be.

3. Ha a workflow hibás

  1. Kattints a piros workflow futásra.
  2. Nyisd meg a build jobot.
  3. Keresd meg az első piros lépést.
  4. Olvasd el a hiba utolsó 5–10 sorát.
Tipikus hiba: ha a health-check nem éri el az alkalmazást, lehet, hogy az alkalmazás nem indult el, rossz porton fut, vagy a Docker build hibás.

4. Cloudflare Pages státuszoldal előkészítése

  1. A repositoryban nyisd meg: status-site/index.html.
  2. Cseréld ki a SAJÁT NÉV és SAJÁT OSZTÁLY részeket.
  3. A GITHUB_REPO_URL helyére írd a saját GitHub repository URL-ed.
  4. A DOCKERHUB_REPO_URL helyére írd a saját Docker Hub repository URL-ed.
  5. Commitold a változást.

5. Cloudflare Pages projekt létrehozása

Záró CloudOps kihívás

„Új kiadás” szimuláció – önálló, de ellenőrizhető feladat

Ebben a részben ugyanazt a folyamatot hajtod végre, amelyet egy valódi új alkalmazásverzió kiadásánál is alkalmazhatnál: forrásmódosítás → image build → registry → Kubernetes rollout → ellenőrzés.

1. Készíts 2.0 verziót

  1. Codespaces-ben nyisd meg a Dockerfile fájlt.
  2. Módosítsd: ENV APP_VERSION=1.0 → ENV APP_VERSION=2.0.
  3. Az app.py főoldalán módosíts egy látható szöveget is, például: CloudLab 2.0.
  4. Mentsd a fájlokat.

2. Buildeld és teszteld helyben

docker build -t cloudlab:2.0 . docker rm -f cloudlab-v2 2>/dev/null || true docker run -d --name cloudlab-v2 -p 8090:8080 cloudlab:2.0 curl http://127.0.0.1:8090/api/info
Akkor jó: a JSON-ban a version értéke 2.0.

3. Töltsd fel Docker Hubra

docker tag cloudlab:2.0 SAJAT_DOCKERHUB_NEV/cloudlab:2.0 docker push SAJAT_DOCKERHUB_NEV/cloudlab:2.0
Ellenőrzés: Docker Hubon az 1.0 mellett már a 2.0 tag is látható.

4. Kubernetes rollout 2.0-ra

Ha a Kubernetes munkameneted lejárt, először állítsd helyre a 4. modul szerint a Deploymentet.

kubectl set image deployment/cloudlab \ cloudlab=SAJAT_DOCKERHUB_NEV/cloudlab:2.0 kubectl set env deployment/cloudlab APP_VERSION=2.0 kubectl rollout status deployment/cloudlab kubectl get pods
Akkor jó: a rollout sikeres, minden új Pod Running állapotú.

5. Ellenőrizd, hogy valóban 2.0 fut

kubectl run v2test --rm -it --restart=Never \ --image=curlimages/curl -- \ http://cloudlab/api/info
Elvárt: "version":"2.0".

6. Skálázás és self-healing

kubectl scale deployment cloudlab --replicas=3 kubectl get pods

Válassz ki egy Podot, majd töröld:

kubectl delete pod POD_NEVE kubectl get pods

Várj néhány másodpercet, és ismét add ki a kubectl get pods parancsot. Ismét 3 Running Podnak kell lennie.

7. Git és CI

git add . git commit -m "CloudLab 2.0 kiadas" git push

GitHub → Actions: ellenőrizd, hogy a 2.0 módosításhoz tartozó CI-futás sikeres.

Ha a Kubernetes még mindig 1.0-t mutat: ellenőrizd a futó image-et: kubectl describe deployment cloudlab | grep Image, majd ellenőrizd az APP_VERSION környezeti változót is: kubectl describe deployment cloudlab | grep -A3 APP_VERSION.
Bizonyíték 16: Docker Hub, ahol az 1.0 és 2.0 tag is látható.
Bizonyíték 17: sikeres Kubernetes rollout és "version":"2.0" API-válasz.
Bizonyíték 18: egy Pod törlése után ismét 3 Running Pod + sikeres GitHub Actions futás.
